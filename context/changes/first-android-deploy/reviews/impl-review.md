### F2 — supabase/config.toml carries local-dev auth defaults

- **Severity**: ⚠️ WARNING
- **Impact**: 🔎 MEDIUM — real tradeoff; pause to reason through it
- **Dimension**: Safety & Quality
- **Location**: supabase/config.toml:164
- **Detail**: Generated by `supabase init`: `site_url` / `additional_redirect_urls` point at `127.0.0.1:3000` (:164, :168), `minimum_password_length = 6` (:187), `password_requirements = ""` (:190), `[auth.email] enable_confirmations = false` (:232); `[db.seed]` points at a non-existent `seed.sql`. Harmless today (applies only to the local stack), but a future `supabase config push` would apply these to the hosted project — and S-01 `account-sign-in` is exactly where auth settings start to matter.
- **Fix A ⭐ Recommended**: Hand it to S-01 as an input — the account-sign-in plan sets real auth values (app scheme redirect URL, password policy, confirmations) and decides whether config.toml or the dashboard is the source of truth.
  - Strength: Settles auth config where the auth requirements are actually designed; no speculative edits now.
  - Tradeoff: Risk stays latent until S-01 is planned.
  - Confidence: HIGH — nothing pushes config today; S-01 is next on the roadmap.
  - Blind spot: Someone running `supabase config push` before S-01.
- **Fix B**: Add a CLAUDE.md rule now: never run `supabase config push` without reviewing `config.toml` auth settings.
  - Strength: Guards agents immediately.
  - Tradeoff: Adds a rule for a command nobody runs yet; may be superseded by S-01.
  - Confidence: MED — prevents the agent path, not a manual push.
  - Blind spot: Manual dashboard vs config drift.
- **Decision**: FIXED via Fix A — queued as an S-01 planning input in follow-ups/review-fixes.md

### F4 — Preview APK and the Play build share one application id

- **Severity**: ℹ️ OBSERVATION
- **Impact**: 🔎 MEDIUM — real tradeoff; pause to reason through it
- **Dimension**: Architecture
- **Location**: eas.json:12
- **Detail**: Preview and production both build `dev.zelazny.follow`. Once F-02 installs the app from Play (re-signed by Play App Signing), a sideloaded preview APK cannot install over it on the same phone without uninstalling — and uninstalling drops the on-device data that S-05 offline marking depends on.
- **Fix A ⭐ Recommended**: Decide in the F-02 plan: either a separate preview application id (e.g. `dev.zelazny.follow.preview` via `app.config.ts` keyed on the build profile) or Play-only installs on household phones.
  - Strength: Decided when the conflict first becomes possible, with Play setup in view.
  - Tradeoff: Moving to `app.config.ts` changes how config is read; must keep typed routes / React Compiler flags.
  - Confidence: MED — standard Expo pattern, not yet checked against SDK 58 docs.
  - Blind spot: Whether OTA channels/fingerprints differ per id.
- **Fix B**: Accept: household phones use only Play builds after F-02; preview APKs only on the emulator.
  - Strength: Zero config change.
  - Tradeoff: Real-device testing of preview builds (S-05 in airplane mode) moves to the emulator or a spare phone.
  - Confidence: HIGH — simple process rule.
  - Blind spot: The Pixel 5 is the PRD's lowest supported device.
- **Decision**: FIXED via Fix A — decision queued for the F-02 plan in follow-ups/review-fixes.md
